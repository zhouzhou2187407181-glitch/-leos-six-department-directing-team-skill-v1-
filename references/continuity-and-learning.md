## 1. 三本账

场记维护三类互相连接但不能混为一谈的记录：

1. **连续性账**：证明相邻镜头和场次在故事世界里能接上。
2. **提示词版本账**：证明每一版最终提示词来自哪些部门定案、吸收了哪些用户意见、相对上一版改了什么。
3. **Take/提示词实验账**：证明某一版提示词产生了什么视频结果，以及下一次为何这样改。

字段设计参考 [ScreenSkills 的场记岗位说明](https://www.screenskills.com/job-profiles/roles/script-supervisor-film-and-tv-drama/) 与 [Script Supervisor Skills Checklist](https://www.screenskills.com/skills-checklists/scripted-film-and-tv/script-supervisor-department/script-supervisor-skills/)：传统场记会持续记录对白、动作、服装、妆发、道具、视线、画面方向、摄影信息和可剪接性。本 Skill 在此基础上增加 AI 生成所需的提示词版本、参考资产、模型参数和输出证据。

连续性账使用 `assets/continuity-ledger-template.csv`；提示词版本账使用 `assets/prompt-version-log-template.csv`；实验账使用 `assets/take-prompt-log-template.csv`。使用项目、场次、镜头组、Prompt 版本和 Take ID 建立关联。

## 2. 连续性状态协议

每个镜头至少记录 `入口状态 → 变化事件 → 出口状态`：

- **人物空间**：位置、朝向、画面方向、相对距离、视线落点、站/坐/跪、动作相位；
- **表演**：进入目标、注意对象、呼吸/声音强度、情绪不是标签而是可见行为；
- **手与道具**：左右手占用、数量、开合、完整/损坏、干湿、是否点燃、是否喝过/吃过；
- **造型**：服装层级、扣子/拉链/袖口、妆发、汗污、血污、伤势位置与阶段；
- **环境**：门窗、车辆、灯具、烟火、桌椅、背景人物、时间、天气和光区；
- **摄影**：轴线、摄影机侧、景别、镜头运动、焦点、画面方向和 eyeline；
- **声音/对白**：台词版本、声音来源、环境声状态和动作声相位。

### 连续性等级

- **硬连续性**：身份、空间方向、关键道具、动作因果、伤势阶段、台词事实。冲突会破坏理解，列为 P0。
- **表演连续性**：目标、注意力、呼吸、动作相位和强度。冲突会破坏真实感，通常为 P0/P1。
- **软连续性**：衣褶、细小背景、轻微手位。核心表演成立时优先剪辑、遮挡或补镜。
- **有意断裂**：越轴、跳切、时间跳跃等导演选择。必须写清意图和建立方式，不能事后把错误称为风格。

### 接镜检查

比较上一镜最后可用帧与本镜第一可用帧，不比较整条素材的默认首尾。差异表写：字段、上一状态、本镜状态、严重级、是否有意、首选修法和验收条件。

## 3. Take 结论协议

每个 Take 使用一个且仅一个主结论：

- **过**：可作为该镜头主版本进入时间线；记录首选可用区间。
- **保**：不是完整主版本，但有稀缺表演、动作、环境或接缝区间必须保存。
- **修**：核心设计成立，存在可定位问题；写明保留区间和最小修法。
- **废**：无可用区间或 P0 根因贯穿整条；仍须记录失败类型，避免重复生成。

结论必须附角色评分或短评：总导演看叙事/节奏，表演指导看行动真实，执行导演看镜内生态，摄影指导看摄影语言，场记看连续性。总导演作最终结论，场记负责原样记录而非改写。

## 4. 提示词实验协议

提示词导演每输出一版最终提示词，先记录：

- 用户的生成授权原话；
- 完整提示词文件、有效字符数与 Prompt 版本；
- 总导演、表演、镜内执行、摄影和连续性设计版本；
- 项目风格档案版本；
- 相对上一版变化、多岗审稿、用户反馈、未解决冲突和批准状态。

实际生成视频后，再记录：

- 完整提示词或可追溯文件；
- 提示词版本、模型/版本、日期、参数和参考资产；
- 相比上一版的唯一主要变化；
- 输出文件、可用时间段、成功点、症状和根因判断；
- 下一版只改的一项、验收条件和结果对比。

优先采用单变量迭代：一次只改变主体动作、时间关系、镜头运动、环境动作、参考资产或模型之一。若必须同时改变多项，标记为 `组合改动，无法单独归因`，不得据此宣称某一词必然有效。

失败分类统一为：导演命题、空间/方向、表演、群戏/环境、动作/物理、连续性、资产污染、提示歧义、模型边界、剪辑/声音、画质。症状与根因必须分开；“人物僵硬”是症状，“没有真实任务”才可能是根因。

## 5. 从记录到知识卡

按以下链条反思：

```text
原始提示词 + 参考资产 + 参数 + 输出
→ 可观察症状/成功点
→ 根因假设
→ 单变量修改
→ 新结果对比
→ 候选经验
→ 证据复核
→ P/O/C 知识卡
→ 更新 Skill 的对应位置
```

候选经验写清：适用镜头类型、触发条件、操作步骤、失败信号、例外、证据 ID、置信度和最后验证日期。先保留反例，不只收集成功样本。

### 证据门槛

- 一次成功/失败：只记观察，不写永久规则。
- 同一镜头的多次随机结果：可形成模型倾向，但仍属于 O。
- 至少两个独立镜头/场次出现同样因果，或导演明确将其定为创作规范：可形成候选 P/C。
- 跨模型仍成立、无关键反例、步骤可复现：才升级为高置信 P。
- 模型版本、参数、价格、时长和成功率始终为 O，并注明 `valid_as_of`。

## 6. Skill 更新门槛

更新时遵循：

1. 在实验账筛选 `知识卡候选=是` 的记录并核对原始素材；
2. 合并重复结论，寻找反例和适用边界；
3. 判断应更新角色职责、表演方法、生成控制、审片路由还是项目配置；
4. 先更新 `knowledge-and-provenance.md` 的知识卡和证据，再修改对应参考文件；
5. 不把原始项目角色或场景设定写成跨项目原则；
6. 运行 Skill 校验，并在知识卡保留 `last_validated`；
7. 若新证据推翻旧结论，标记“已修正/已降级”，不要静默覆盖历史。

用户对某个项目的口味、摄影规则或提示词偏好默认写入 `assets/project-style-profile-template.json`，类型为 C。一次反馈先记 `candidate`；用户明确确认或本项目多例成立后记 `confirmed`。不要把项目偏好直接写入通用 Skill，也不要让提示词导演自行改写 Skill。

定期复盘不是按固定交付节奏执行；用户提供一批新审片/生成记录或明确要求更新时再运行该闭环。
